## Changes and write ownership

| Operation | Single local write path | Result |
| --- | --- | --- |
| Metadata | `FieldProvider.saveFieldLocally` → shared awaited save helper → `FieldStorageService.saveField` | Local errors reach UI; Cloud is queued separately; metadata produces no measurement |
| Boundary edit | `saveBoundaryLocally` → `saveBoundaryAndMeasurement` → SQLite transaction | Field and measurement commit or roll back together; current metadata is retained |
| Measured field creation | `createMeasuredFieldLocally` → same measured transaction in create mode | GPS/manual screens wait for both rows, instead of announcing success early |
| Photos | `saveFieldPhotosLocally` → shared awaited save helper | Add/remove list mutations are persisted; failed operations retain the prior list |
| Delete | `FieldDatabase.deleteIn` transaction | Field and local measurement history are removed together or neither is removed |
| Restore | Serialized replace, with per-field rollback ownership | Failed restore restores its prior values without overwriting a newer edit |

The measured-history identity is derived from field ID, measured date and
measurement geometry/metrics. Retrying one measured snapshot preserves its
history identity and original creation time. A different measured date or
geometry produces another entry. No V2 Spatial schema, revision rule, parcel
identifier, household code or projection authority is changed.

The photo remove button previously built an unused local list. It now awaits
the parent persistence callback. Removing a reference does not delete the
underlying media file, which may be shared with other records or backups.

`main.dart` contains startup, localization and application composition. The
old dashboard is isolated in `app/legacy_dashboard.dart`; its public classes
remain re-exported so compatibility callers keep working. Production startup
selects `CompanyAccessGate` without registering legacy business providers.
`MyApp.legacy()` explicitly mounts the compatibility dashboard and its provider
scope above MaterialApp/Navigator, so pushed legacy routes retain access.
`homeOverride` alone does not opt into legacy stores. The former global-provider
test contract is intentionally replaced: default startup asserts their absence,
while the explicit compatibility test retains their registration assertions.

## Overlap audit — keep explicit boundaries

| Area | Current V2 authority | Compatibility code and disposition |
| --- | --- | --- |
| Land | `LandParcel` repositories and Spatial write/link guards | `FieldModel`/`fields` remain a separate legacy model. No guessed ID mapping or automatic geometry copying |
| Catalog/resources | Company catalog; existing resource projections reused | Legacy machine/worker comparison imports only explicitly reviewed, verified selections |
| Inventory | `InventoryService` and `inventory_items_v2`/movement ledger, linked to shared material catalog | Warehouse provider remains compatibility code; do not sum its balances into V2 inventory |
| Tasks | `FarmTaskService`/`farm_tasks_v2` with parcel and work links | Old TaskProvider is not the V2 task authority; deleting it requires a separate migration/parity decision |
| Finance | V2 finance documents and document-linked cost reports | Legacy finance/cost providers remain compatibility modules; do not combine totals without provenance |
| Backup | V2 local backup and catalog restore barrier | Legacy Cloud restore is a separate compatibility workflow, not a replacement for the catalog sync protocol |
| Entry/routing | Company access gate and V2 composition | Legacy providers are registered only through the explicit `MyApp.legacy()` entry |

These are not interchangeable duplicate stores. Removing compatibility modules
before migration and feature parity would delete functionality and break restore
contracts. This cleanup isolates and hardens them; it does not claim complete
legacy removal or full unification of every ERP module.

## GPS draft boundary — follow-up

Both V2 GPS entry points (existing parcel and creation) use the explicit
`FieldGpsMeasureScreen.draft()` mode. The existing-parcel entry previously
used the legacy default, which persisted an unrelated `FieldModel` before
showing the V2 boundary preview. Draft mode returns the completed measurement
without initializing FieldProvider or saving fields/history/Cloud data.
The existing V2 preview and guarded commit workflow remains the write authority;
cancelling measurement or preview does not create a legacy field.

Legacy GPS entry keeps the default persisted mode and awaits the atomic local
field/history write. GPS service and map substitutions permit deterministic
widget tests without real location, maps, database or Cloud access. Tests cover
returned draft geometry, cancellation, awaited legacy persistence and failure.
No coordinate calculation, schema, parcel identity or Spatial guard is changed.

## Existing legacy field GPS remeasurement

The field detail action labelled measure/update previously opened the create
workflow and produced another GPS field. It now selects explicit `forField`
mode. The same field ID goes through `saveBoundaryLocally`, preserving the
latest metadata and photo references and awaiting atomic boundary/history
persistence. The dialog identifies the target instead of offering metadata
edits that a boundary operation does not own. A deleted target is rejected;
remeasurement cannot silently recreate it. V2 remains in draft mode and the
legacy list action remains the explicit new-field flow.

## GPS local-save retry

After a local save failure, GPS measurement retains its pending field ID,
measurement date and entered name/crop. Retrying the same points reuses that
measurement identity; SQLite history deduplication can recognize the snapshot.
Removing a point, receiving a new distinct point or starting a new measurement
invalidates the pending snapshot. Both create and existing-field retry modes
have widget coverage. Manual measurement retry remains a separate follow-up.
